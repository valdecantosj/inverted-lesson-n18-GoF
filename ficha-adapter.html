Patrón Adaptador (Adapter)

Problema Central

¿Cómo resolver interfaces incompatibles o proporcionar una interfaz estable para componentes con interfaces diferentes sin modificar el código preexistente?

Solución de Diseño

Introducir un objeto intermedio (Adapter) que implementa la interfaz esperada por la aplicación (Target) y traduce las llamadas a los métodos del componente incompatible (Adaptee).

Ver Participantes Formales (UML)
  • Client: Clase del dominio que requiere el servicio y colabora con Target.
  • Target: Interfaz común que define el contrato del sistema interno.
  • Adapter: Fabricación Pura que implementa Target y traduce la invocación.
  • Adaptee: Componente externo con interfaz incompatible que hace el trabajo real.

Mecánica de Traducción de Métodos

// Target conocido por el sistema: public interface IPago { ResultadoPago procesarPago(double monto); } // Adaptador traduciendo al Adaptee (MercadoPagoSDK): public class MercadoPagoAdapter : IPago { private MercadoPagoSDK _sdk; public ResultadoPago procesarPago(double monto) { // Traduce sintaxis y nombres de operaciones return _sdk.realizarTransaccion(monto); } }
⚠️ Precaución de Diseño: El Problema del "Voltaje"

Un adaptador hace compatibles las firmas de métodos (sintaxis), pero no garantiza por sí solo la semántica. Si el sistema envía pesos y el servicio externo espera centavos, o si arroja excepciones de bajo nivel no normalizadas, el adaptador debe contener la lógica de conversión y manejo de fallos para evitar caídas catastróficas.

Fundamento GRASP

El Adaptador materializa tres directivas esenciales de la Unidad 5:

  • Indirección: Introduce un objeto intermediario para evitar la dependencia directa.
  • Polimorfismo: Permite intercambiar proveedores de servicio sin alterar el cliente.
  • Variaciones Protegidas: Oculta la inestabilidad de las APIs de terceros detrás de una interfaz fija.
